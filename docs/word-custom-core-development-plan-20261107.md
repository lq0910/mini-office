## 1. 已确认的技术方向

**GenOffice 的 Word 技术基础 → Mini Office 的定制内核 → 我们持续开发和维护。**

以用户对 GenOffice 的验证为前提，直接进入源码融合开发，不再设置 GenOffice 选型、兼容能力证明或完整应用试接阶段。后续测试检查的是融合后的 Mini Office，尤其是本项目的文件生命周期、平台接口和 UI 对接。

接入的是 Word 的完整技术链路：DOCX 解析、原始部件保留、文档模型、编辑事务、选区、撤销重做、表格、字体与段落布局、分页、保存。以这些实现为基础形成我们维护的模块，后续可以重构、修复和扩展，不把它作为不可修改的黑盒。

### 必须保留

- Mini Office 现有工具栏的整体布局、标签、按钮、主题和交互风格。
- 首页、文件标签、工作区、命令面板、状态栏和现有文件管理。
- 现有 Tauri 桌面框架、原子写入、文件备份、最近文件与恢复快照机制。
- 当前 Word 已有功能的产品入口。切换前逐项完成新核心实现，不能仅保留可点击的空入口。
- Excel、PPT 及预览模块的现有行为。

### 接入范围

- 继承 Word 核心的数据结构与配套规则；不要先转成当前简化 `DocModel` 再编辑、保存。
- 对上游代码做模块拆分和接口改造，命令直接融入我们的 Word 模块。
- 字体、图片、编号、公式或图表等 Word 内容所需的传递依赖可以引入；不因此加载整个其他编辑器。
- 必要且实用的新增操作优先放进现有表格上下文工具或右键菜单，保持现有 UI 风格。

### 本轮不做

- 不替换整套产品为 GenOffice，不引入它的应用外壳、首页、Ribbon、AI 面板或其他编辑器界面。
- 不采用隐藏上游工具栏的完整应用嵌套，也不以 iframe 或独立应用窗口作为默认产品结构。
- 不新建跨编辑器的通用命令总线、RPC 框架或完整 `window.desktop` 仿真层。
- 不重新从零实现上游已有的编辑事务、Word 模型与分页算法。
- 不把本轮范围扩展为全项目 React 升级、Electron 迁移或 Rust 文档内核重写。

## 3. 目标代码边界

以下是目标职责结构。M1 已建立 `packages/word-core`，上游衍生源码暂按原目录保存在 `src/upstream` 以降低改动成本；我们自己的会话、序列化、排版调度及平台端口已分目录实现。后续再逐步整理，不进行无行为依据的大规模重排。

```text
packages/word-core/                 Mini Office 维护的定制 Word 内核
  UPSTREAM.md                     固定提交、提取范围、来源与修改说明
  src/document/                   上游衍生的完整模型、来源锚点和原始包
  src/editing/                    编辑 schema、事务、选区、历史与表格操作
  src/layout/                     行盒、表格布局、分页、分节和字体规则
  src/serialization/              编辑状态到保存计划、原始 XML 与部件回写
  src/session/                    文档生命周期、修订版本与保存确认
  src/platform/                   Word 所需的具体平台能力定义

packages/editor-word/src/          Mini Office 的 Word UI
  WordEditor.tsx                  挂载核心、组织现有工具栏及界面
  WordToolbar.tsx                 保留现有 UI，消费格式与选区状态
  …现有对话框、面板、上下文菜单

packages/document-model/           工作区会话、文件元信息和修改状态
packages/platform-adapter/         Tauri / Web 文件、字体及系统能力
apps/desktop/src/format-handlers.ts Word 格式的按需加载入口
```

依赖方向：`editor-word → word-core`；工作区可以使用核心的类型和会话入口。`word-core` 不依赖 `editor-shell`、旧 Word UI 或工作区 store，避免循环依赖。运行中的编辑器、DOM 和字体缓存留在会话运行时，不塞入需要持久化的工作区 JSON。

初期尽量保留上游文件内部的结构，优先切开 App、UI 和平台耦合。完成行为对接后，再按职责重命名和整理，避免同时大规模改结构、改模型、改算法。

### React 与编辑宿主

优先以框架无关的 Tiptap/ProseMirror 编辑运行时挂载到我们 React 18 组件提供的元素。上游的纯 DOM 编辑扩展、模型转换与排版代码可以保留，App 中的状态协调逻辑提取到会话控制器；不直接移植 React 19 的完整 App。

M1 核对完整依赖闭包及 NodeView 实现。若某一必需能力确实依赖 React 视图，仅局部移植该视图并适配现有运行时，不为解决一个组件直接升级整套应用。不能把只挂载一个默认 Tiptap 编辑器当作上游 Word 核心已经接入。

### 命令直接融合

保留 `onInlineCommand`、`onFontFormat`、`onParagraphFormat` 等现有回调入口，内部直接调用定制核心的命令。无须额外构建一套通用适配层；接口转换可以放在现有事件处理函数和 Word 核心内部。

允许使用小范围的类型/单位转换，例如把工具栏字号转成核心单位，把核心选区状态映射成按钮状态。这样的 UI 状态映射不能演变成把整份文档转回旧模型。

命令应正确作用于当前活动编辑区域，包括正文、表格格内、页眉页脚或文本框；不能统一误发给正文编辑器。工具栏操作需要保持选区，回填格式状态，并处理混合字号、混合字体和不可执行操作。

## 5. 集成验收标准

不以测试数量或能打开文件作为整体完成标准。验收至少包含以下结果：

1. **UI 保留**：现有工具栏、主题、标签与主界面保持产品风格，常用操作入口仍然可用。
2. **编辑正确**：中文确认/取消不留下拼音；跨段跨页选择、粘贴、表格编辑和撤销重做不丢内容或错误定位。
3. **保存正确**：无实际修改时按支持场景保持原始字节；文字修改保留非目标结构。结构编辑只允许产生预期变动，保存后关系、合并单元格、边框和样式仍有效。
4. **连续操作正确**：修改 → 保存 → 再编辑 → 再保存 → 重开，以及撤销/重做后的保存都正确；保存期间继续输入不会被完成回调覆盖。
5. **生命周期正确**：标签切换、非活动文档保存、快照恢复、另存为取消、磁盘写入失败和关闭确认均不丢正文。
6. **平台融合正确**：真实桌面中文输入、系统字体、图片资源、打印和导出可用。浏览器测试不能替代桌面验收。
7. **格式兼容正确**：用用户业务文档的副本检查融合后的保存件在 Word 中打开、表格与分页表现；既有原件及备份不被测试覆盖。上游本身的已知限制与本项目引入的回归分别记录。

私人样本通过显式外部路径读取，副本和结果写入忽略目录；不将业务报告、历史备份或截图中的私人内容加入公共夹具。当前验收报告中已经损坏的文字和边框，单独作为已有损坏记录，不能用它要求新核心凭空恢复。

检查安排：模型和补丁保存用定向 Vitest；操作和 UI 状态用组件/浏览器回归；原生平台变更运行对应 Rust 检查；阶段合入前运行 `pnpm typecheck`、相关测试和 `pnpm build`；默认切换前运行全量检查、桌面构建及上述实际验收。没有实现改动时，不重复运行全部测试来替代开发进度。

## 6. 后续自主维护规则

- 我们的定制核心源码只有一个主维护位置；上游固定提交、提取清单和修改记录足以重建原始基线，避免同时修改两份同功能源码。
- 每次引入或更新上游记录提交、来源文件、必要依赖、资源和行为变化。按需合并已知修复，不直接随 `main` 自动升级。
- 优先在会话、命令与平台结合处定制。需要修改解析、模型、编辑 schema 或布局算法时，配套记录原因与可复现回归。
- 新功能直接基于定制核心实现，避免继续给旧模型增加第二份功能；工具栏始终调用同一核心。
- 保留原作者、来源和原有许可信息，登记本地修改。新增或修改代码按用户要求写明功能、时间、作者 `lq`，不覆盖原作者信息。
- 资源精简按实际引用和场景检查进行；不盲目删除未在当前样本出现的 Word 格式支持。字体和其他第三方资源分别记录来源，不默认全部随仓库根许可处理。
- 优先按需加载 Word、后台解析和增量重排。旧路线图中的体积与性能数值保留为目标，M1 建立实际基线，不能以删减必需排版规则换取数字达标。
