Word 现按 **GenOffice 的 Word 技术基础 → Mini Office 的定制内核 → 我们持续开发和维护** 推进。以用户对上游的验证为前提，直接融合完整 Word 核心链路，保留 Mini Office 工具栏、UI、Tauri 与文件管理；必要命令直接融入现有 Word 模块，不额外建设通用适配系统。

具体任务、代码边界、阶段交付与验收见 [Word 定制内核开发计划](word-custom-core-development-plan-20261107.md)。本页后续关于 Word 的样本选型、局部规则移植、最小模型及 Rust 核心替代等内容作为历史背景；如有冲突，以该计划为准。Excel、PPT 等其他格式的现有路线不因本次 Word 调整而自动变更。

2026-11-08 已完成 M0 基线整理及 M1 核心提取，交付见 [M0 记录](word-core-m0/README.md)和 [M1 记录](word-core-m1/README.md)。定制 `word-core` 可独立构建，现有产品 Word 页面与工具栏仍保持原实现，M2 产品接线待实施；模块构建通过不能计作默认内核已经切换。

## 目标

Mini Office 的定位是“小而美”：启动快、安装包小、离线可用、常用文档打开后能正常编辑和导出。当前重点是以 GenOffice 的成熟样本和实现为参考，逐步实现接近原版 Office 的文档高保真解析、显示、编辑与保存；不再以未经样本验证的笼统兼容百分比作为验收依据。

目标优先级如下：

1. 常见文件打开成功，正文、表格、图片、页眉页脚和主题样式基本可见。
2. 常见编辑操作不破坏未修改内容。
3. 重新打开和导出后的页面数量、主要位置和颜色稳定。
4. 复杂对象可保留或明确提示，不静默丢失。
5. 体积、启动速度和内存占用保持在轻量应用范围内。

## 约束和预算

### 体积预算

- 主程序新增解压后体积目标：不超过 15 MB。
- 单个平台安装包增长目标：不超过 25 MB。
- 不内置完整 LibreOffice、Chromium 或大型字体包。
- 字体优先使用系统字体；仅为缺失的关键字体提供可选下载。
- DOCX、XLSX、PPTX 解析能力按格式拆分，避免打开一个格式时加载全部引擎。

### 性能预算

- 普通 10 页 DOCX 首屏目标：1 秒内显示正文。
- 普通 20 页 PPTX 首屏目标：1 秒内显示第一张幻灯片。
- 10 万行以内 XLSX 首屏目标：2 秒内显示可交互网格。
- 解析过程不能阻塞界面线程；大文件、图片解码和布局计算放入 Rust worker 或后台任务。

### 兼容性边界

优先支持：

- DOCX：段落、字符样式、列表、表格、图片、页眉页脚、页码、分节、文本框、常见形状。
- XLSX：工作表、单元格、公式结果、数字格式、合并单元格、冻结窗格、筛选、基础条件格式和打印区域。
- PPTX：幻灯片、主题色、母版占位符、文本框、常见形状、图片、表格、组合对象和备注。
- 旧格式：`.doc`、`.xls`、`.ppt` 优先实现读取和转换，不承诺原格式写回。

暂不追求：宏执行、复杂 SmartArt 编辑、复杂动画编辑、嵌入 OLE 对象编辑、数字签名继续有效、完全复刻 Office 的高级排版算法。

## 技术路线

### 1. 接入 office_oxide 作为旧格式和底层格式补强

`office_oxide` 是纯 Rust Office 文档库，支持 DOCX、XLSX、PPTX 以及旧版 DOC、XLS、PPT 的统一读取接口。旧格式以读取和转换为主，现代 OOXML 才进入可编辑路径。

接入原则：

- 先以独立 Rust crate 方式接入，不替换现有 React 编辑器。
- 通过 Tauri command 暴露“识别、读取摘要、转换为 OOXML”的最小接口。
- 只在旧格式或现有解析器无法识别时调用，避免普通文件增加启动成本。
- 转换后的文件保留原始文件名、来源和兼容性提示。
- 评估依赖树、许可证和最终二进制大小后再决定是否纳入默认构建。

第一阶段不直接让 office_oxide 接管所有渲染，避免把一个尚未验证的完整引擎引入关键编辑链路。

### 2. 重构当前 OOXML 层为“保留包 + 可编辑 IR + 布局层”

当前 TypeScript 解析器适合快速实现，但把文件转换为简化模型后再重新序列化，容易丢失未知部件。重构目标是保留当前 UI，同时调整底层边界：

```text
office-core
├── package        ZIP/OPC 包、关系、内容类型、部件保留
├── theme          主题色、主题字体、色彩变换
├── units          EMU、twips、points、像素的统一换算
├── model          可编辑的文档中间表示
├── layout         分页、换行、表格和对象定位
├── render         HTML、Canvas、PDF 统一绘制接口
├── docx           Word 部件和样式解析
├── xlsx           工作簿、公式和打印布局解析
└── pptx           母版、占位符、形状和文本布局解析
```

仓库中已有 `crates/office-core`、`crates/office-ooxml`、`crates/office-doc`、`crates/office-sheet` 和 `crates/office-slides`，后续优先把它们作为 Rust 核心的承载位置，逐步替代重复的 TypeScript OOXML 基础逻辑。

### 3. 采用最小可用中间表示

中间表示只保存编辑器需要修改的字段，同时保留：

- 原始部件字节或 XML 片段。
- 原始关系 ID 和部件路径。
- 未识别节点的位置和哈希。
- 对象的来源 ID。
- 能力级别和潜在丢失项。

保存时优先替换被编辑的节点，未修改部件直接复用原始内容。这样能在不实现所有 OOXML 特性的情况下减少格式损失。

### 4. 布局能力按高频问题建设

不追求一次性实现完整 Office 排版，而按用户反馈和文件样本优先级实现：

1. 字体、字号、颜色、行距、段前段后和对齐。
2. 页边距、纸张方向、分节、页眉页脚和页码。
3. 表格列宽、行高、合并单元格、边框和重复标题行。
4. 图片尺寸、锚点、环绕和常见形状。
5. PPTX 主题色、母版占位符、文本框内边距和组合对象变换。
6. XLSX 打印区域、分页、数字格式和条件格式。

每项能力都需要同步加入解析、渲染、保存和回归测试，避免只修复预览而破坏保存。

## 分阶段计划

### 阶段 A：基线和接缝（1 周）

- 固定现有 TypeScript 行为和测试结果。
- 为三种格式增加统一的兼容性报告字段。
- 测量当前主程序、Tauri 二进制和按格式代码的体积。
- 建立 30 个最小真实样本：10 个 DOCX、10 个 XLSX、10 个 PPTX。
- 明确 Rust crate 与现有 TypeScript handler 的调用协议。

验收：不改变现有 UI 功能，能够输出每个文件的格式、能力等级、未知部件和风险提示。

### 阶段 B：office_oxide 旧格式通道（1–2 周）

- 增加 `.doc`、`.xls`、`.ppt` 的识别和只读摘要。
- 支持旧格式转换到 OOXML 临时文件。
- 在打开流程中增加“转换后编辑 / 只读查看”选择。
- 限制解压大小、条目数和内存使用。
- 测量增加的二进制体积和启动耗时。

验收：旧格式至少可以读取文本、表格或幻灯片摘要；转换失败时给出明确原因，不影响现代格式打开。

### 阶段 C：OOXML 包保留和主题基础层（2–3 周）

- 统一 ZIP/OPC 读取、关系解析、内容类型和路径规范化。
- 统一主题色、色彩变换、主题字体和字体回退。
- 为 DOCX/PPTX/XLSX 保留未知部件和原始关系。
- 将重复的单位转换和 XML 工具迁移到 `office-ooxml`。

验收：打开后不编辑再保存，未修改部件哈希保持不变；主题色和字体样本通过视觉对比。

### 阶段 D：DOCX 高频布局（3–5 周）

- 完善样式链、分节、页眉页脚、表格网格和分页。
- 增加浮动图片、文本框、段落边框和常见字段。
- 统一 HTML 预览和 PDF 导出使用的布局结果。
- 处理复杂对象时保留原部件并显示兼容性提示。

验收：常见合同、通知、报告样本的页数和主要版式达到 70% 以上一致；编辑普通文本后原表格和页脚不丢失。

### 阶段 E：PPTX 高频布局（3–5 周）

- 完善母版、布局、主题和占位符继承。
- 支持文本框内边距、字体回退、颜色变换、组合对象和常见形状。
- 对复杂动画、SmartArt 和媒体保留原始部件。

验收：标题页、图文页、表格页和主题色样本达到 70% 以上视觉一致；保存后能被 PowerPoint/WPS 正常打开。

### 阶段 F：XLSX 和打印布局（3–5 周）

- 补齐数字格式、日期系统、合并单元格、打印区域和分页。
- 公式先复用现有计算引擎，Rust 侧只补格式和依赖关系。
- 复杂图表、透视表和宏保持原始部件并报告风险。

验收：常见台账、报表和简单公式样本打开、编辑、保存、重开稳定。

## 质量门槛

每个版本都必须通过：

- 真实文件打开成功率 ≥ 95%。
- 高频功能样本的版式可用率 ≥ 70%。
- 普通文档首屏时间不回退超过 20%。
- 主安装包增长不超过预算。
- 未修改部件保留率 ≥ 95%。
- 保存后的文件可被 Microsoft Office、WPS 或 LibreOffice 重新打开。
- 所有新增解析器都通过 ZIP 炸弹、超大 XML、恶意关系和异常图片测试。

## 体积控制手段

- Rust release 开启 `lto = "thin"`、`strip = "symbols"`、`opt-level = "z"`，在体积和速度之间取平衡。
- 采用 Cargo feature 拆分 `docx`、`xlsx`、`pptx`、`legacy` 和 `pdf`。
- 只在需要时加载对应格式的 WASM 或原生模块。
- 不内置完整字体包，使用系统字体和可选字体缓存。
- 不把 Office 原始部件复制进安装包，只在用户文件中处理。
- 每次构建记录安装包、二进制、WASM 和资源体积，超过预算直接阻止发布。

## 最终决策

当前选择：

1. 先接入 `office_oxide`，解决旧格式读取和转换。
2. 保留现有前端和编辑体验，不进行全量重写。
3. 以仓库已有 Rust crates 为新 OOXML 核心的承载位置。
4. 先完善包保留、主题、DOCX 高频布局，再推进 PPTX 和 XLSX。
5. 以 70% 高频兼容度、15 MB 主程序增量和 20% 性能回退上限作为发布门槛。

不将 WPS 全量能力作为目标，不引入完整 LibreOffice，不在没有真实样本和体积数据前承诺高保真兼容。
